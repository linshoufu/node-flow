## 执行策略与重试

节点在右侧配置面板的「失败处理」区域可设置运行策略（工作台当前只呈现节点配置本身，策略字段由工作流文档保存并由执行器读取）：

| 策略 | 行为 |
| --- | --- |
| `失败即停止` | 默认行为，节点失败后结束本次工作流运行。 |
| `失败后继续` | 记录失败和「错误已处理」事件，但不向下游输出数据；其他独立分支可继续执行。 |
| `走错误端口` | 仅适用于声明并连接 `error` 输出端口的节点。运行时把标准错误对象传给该端口的下游节点。 |
| `最多尝试次数` / `重试间隔` | 单节点可配置 1 到 5 次尝试、0 到 60 秒间隔。运行详情会显示每次尝试与「已安排重试」事件。 |

标准错误对象包含 `message`、`type`、`attempt`、`nodeId`、`scope` 和 `timestamp`。工作流默认 600 秒全局超时，保存在工作流文档的 `settings.timeout_seconds`。

**固定调试输出**（`pinnedData`）由执行器读取：手动运行时跳过该节点实现并直接发布固定输出，同时写入 `node_pinned_data_used` 事件。Webhook 请求和 `workflow.execute` 创建的子运行以 `allow_pinned_data=False` 执行，始终忽略固定数据。字段契约见[节点契约说明](node-contracts.md#固定调试输出)。

## 错误处理工作流

工作流文档的 `settings.error_workflow_id` 指向一个已保存的错误处理工作流。该工作流必须仅以一个 `工作流触发` 节点开始。

当前工作流失败时，系统会创建一条独立的「错误处理」运行，并把失败运行 ID、工作流 ID、名称、版本和已脱敏的错误信息传给该触发节点。运行日志记录错误处理的启动、成功、失败或跳过。错误处理运行使用自己的全局超时，不会因当前运行的超时被立即取消；取消当前运行也不会触发它；它自身失败不会递归触发下一层。

错误处理工作流拥有独立的跨运行状态事务，因此可以在主流程失败后持久化自己的告警或去重状态。

## 版本、发布与回滚

每次保存和节点升级都会保留历史版本；发布或停用只切换生产版本指针，不会额外创建版本。

| 接口 | 用途 |
| --- | --- |
| `GET /api/workflows/{id}/versions` | 列出历史版本 |
| `GET /api/workflows/{id}/versions/{version}` | 读取指定版本内容 |
| `POST /api/workflows/{id}/versions/{version}/restore` | 以历史版本内容生成一个新的草稿版本 |
| `POST /api/workflows/{id}/versions/{version}/rollback` | 把历史内容复制成新的已发布版本并立即切换生产入口 |
| `GET /api/workflows/{id}/publication` | 读取生产版本、草稿版本与是否有未发布修改 |
| `POST /api/workflows/{id}/activation` | 发布或停用（切换生产版本指针） |

新保存的工作流默认是未发布草稿，避免在配置未确认时暴露外部触发器。恢复不会覆盖历史，而是校验后生成新版本；恢复或节点升级后需要再次发布才会影响外部触发器。发布时会执行 Webhook 路由冲突校验；未发布工作流、当前版本和已经在生产运行的版本不能回滚。版本记录会标注「普通保存」「恢复自 vX」或「生产回滚自 vX」。

保存、发布、恢复、回滚和升级都携带 `X-Workflow-Expected-Version` 请求头。版本不一致时接口返回 `409`：

```json
{
  "detail": {
    "code": "workflow_version_conflict",
    "message": "工作流已被其他操作更新，请重新加载后再保存。",
    "expected_version": 3,
    "current_version": 5
  }
}
```

工作台把这个响应转换成可见的失败提示与「重新加载服务器版本」「另存为副本」两条恢复路径；直接调用 API 时需要自行处理该冲突。

## 节点版本升级

工作流会为每个节点保存 `typeVersion`。新拖入的节点记录当前 Python 节点脚本的 `@node(..., version=...)` 版本；旧工作流未保存版本时按 v1 处理。

| 接口 | 用途 |
| --- | --- |
| `POST /api/workflows/{id}/upgrades/preview` | 预览字段级新增、修改、删除与每一步迁移说明 |
| `POST /api/workflows/{id}/upgrades/apply` | 应用升级并写入新的草稿版本 |

当节点脚本调整配置模型并提高版本号时，需要为每一步迁移提供 `migrate_config`；系统按版本顺序逐步执行，并在最终配置不符合当前 Pydantic 模型、缺少迁移步骤或节点版本倒退时阻止应用。迁移函数的写法见[节点开发指南](node-authoring.md#节点版本升级)。

历史运行的「重新运行」会先校验其保存工作流中的节点版本；若当前脚本已经不兼容会拒绝创建重试。已经排队、恢复或由 Worker 延后领取的运行会在真正启动前再次检查，发现节点缺失或版本不兼容时明确失败，不会混用新脚本与旧配置。

## 触发器状态与调试监听

| 接口 | 用途 |
| --- | --- |
| `GET /api/workflows/{id}/triggers` | 生产版本启停状态、Webhook 绑定与定时器下次执行时间 |
| `POST /api/workflows/{id}/webhook-test/listen` | 为指定节点启动调试监听 |
| `GET /api/workflows/{id}/webhook-test/listen/{node_id}` | 查询监听状态 |
| `DELETE /api/workflows/{id}/webhook-test/listen/{node_id}` | 停止监听 |

**定时触发**调度器按节点的 `interval_seconds`（10 秒到 7 天）等待一个完整间隔后创建运行，下次执行时间持久化到 SQLite，服务重启后继续使用原有时间。触发数据包含 `trigger: "schedule"` 与 `scheduled_at`。

**调试监听**对应调试地址 `POST /webhooks-test/<工作流 ID>/<path>`，它精确调用最近保存的草稿版本，即使尚未发布。监听在两分钟后过期，并在收到一条请求后自动结束，不会执行未保存的画布改动。

## 运行控制与恢复

| 接口 | 用途 |
| --- | --- |
| `POST /api/workflows/{id}/runs` | 创建运行（可带 `entry_node_id`、`initial_input`、`environment_id`） |
| `GET /api/workflows/{id}/runs` | 运行列表，支持 `limit`、`offset`、`status` |
| `GET /api/runs/{id}` | 单次运行详情 |
| `GET /api/runs/{id}/queue` | 排队位置与全局执行占用 |
| `POST /api/runs/{id}/cancel` | 取消运行 |
| `POST /api/runs/{id}/retry` | 重新运行 |
| `GET /api/runs/{id}/events` | 运行事件（`after_id` 可增量拉取） |
| `GET /api/runs/{id}/events/stream` | 运行事件流 |

**取消是协作式的**：排队中的运行取消后立即从队列移除并标记为「已取消」；已经开始执行的运行会先让当前 Python 节点返回，执行器随后停止未开始的节点和循环迭代，不强杀节点。

**重新运行**会严格复用该次运行保存的工作流版本、入口节点、触发输入与固定数据设置，而不是当前画布；新的运行记录标为「手动运行」，原运行与重试运行的事件互相链接。为避免重复的外部副作用，生产/调试 Webhook、子工作流和错误处理运行不提供重试入口。

**服务重启恢复**：运行创建时会保存工作流版本、入口节点、触发输入和启动方式。服务重启后，尚未开始的手动或定时运行会从保存的版本继续执行；正在执行中的运行、Webhook 请求和子工作流不会自动重放（它们可能已经产生外部副作用），会被标记为失败并在运行事件中记录中断或跳过恢复的原因。

## 队列、并发与独立 Worker

服务端默认最多同时执行 4 个运行，超过上限的手动、定时或恢复运行保持「排队中」，直到获得执行槽位。工作流可在 `settings.max_concurrency` 中设置自己的同时运行上限：留空表示只受全局队列限制；设为 `1` 时，同一工作流的手动、定时与 Webhook 根运行会串行执行，其他工作流仍可使用剩余额度。Webhook 在「等待工作流完成」模式下同步等待自己的工作流，以便返回节点定义的 HTTP 响应。

默认 `embedded` 模式适合本地单进程使用，API 服务同时消费队列。需要把执行与 API 隔离时，先以 worker 模式启动 API，再单独启动 worker：

```powershell
$env:NODE_FLOW_EXECUTION_MODE = "worker"
pnpm dev:api

# 新开一个终端，使用同一个 SQLite 数据库
pnpm dev:worker

# 或自行指定数据库、节点目录和并发数
python -m apps.api.nodeflow_api.worker --database node-flow.sqlite3 --nodes-dir nodes --concurrency 4
```

独立 worker 只领取手动和定时触发创建的后台根运行，并通过 SQLite 原子领取和租约标记防止多个 worker 重复执行。Webhook 与子工作流保持同步执行语义。API 重启不会中断仍由独立 worker 持有租约的运行；worker 进程本身失联后的运行不会自动重放。

Worker 会在每次领取任务前检查 `nodes/` 下 Python 节点脚本和 `nodeflow-package.json` 清单的文件变更；已开始的运行继续使用启动时的节点快照，后续领取的运行使用刷新后的定义。

Worker 的 `--concurrency` 是所有连接同一 SQLite 数据库的 Worker 共享的全局上限，而不是每个进程可叠加的额度；同一部署中的 Worker 应使用相同配置，并与 API 服务的全局队列限制保持一致。

## 运行环境与变量

| 接口 | 用途 |
| --- | --- |
| `GET` / `POST /api/project-variables` | 列出 / 新建项目变量 |
| `PATCH` / `DELETE /api/project-variables/{name}` | 修改 / 删除项目变量 |
| `GET` / `POST /api/project-environments` | 列出 / 新建运行环境 |
| `PATCH` / `DELETE /api/project-environments/{id}` | 修改 / 删除运行环境 |

每个环境保存一组 JSON 变量，工作流表达式通过 `{{ project.xxx }}` 读取当前环境中的值。环境也可以建立「工作流凭据 → 环境实际凭据」的同类型映射：节点中固定引用「默认 HTTP 令牌」，在测试环境映射为「测试 HTTP 令牌」，发布环境映射为「生产 HTTP 令牌」，工作流不需要改动凭据字段；映射只保存凭据 ID，不保存或展示秘密值。

生产 Webhook 与定时触发使用已发布版本所选的环境；手动运行可在创建运行时通过 `environment_id` 临时指定。每条运行都会记录环境 ID、环境名称、变量快照和凭据映射快照，环境后续修改、删除或重命名不会改变已有运行。变量仅用于非敏感配置；令牌、密码和鉴权头应使用凭据库。

## 凭据存储

凭据在 Windows、macOS、Linux 上统一使用 AES-256-GCM。SQLite 保存带版本标识的密文、随机 nonce 和认证标签；服务密钥保存在进程环境或独立文件中，不写入数据库、工作流或日志。相同服务密钥可以在不同系统上解密相同的服务密文。

| 环境变量 | 行为 |
| --- | --- |
| `NODE_FLOW_CREDENTIAL_KEY` | 32 字节随机密钥的标准 Base64 编码；由部署环境的密钥管理功能注入 |
| `NODE_FLOW_CREDENTIAL_KEY_FILE` | 独立密钥文件路径，内容为同样的 Base64 编码；路径支持用户目录展开 |

密钥环境变量和密钥文件配置只能选一个，同时设置会明确失败。两者都未设置时，服务首次保存凭据会自动创建当前用户目录的 `.node-flow/credential.key`，API 与 Worker 共享此默认文件；导入模块或启动空服务不会创建密钥文件。首次并发创建采用完整临时文件的原子发布，不覆盖已有密钥。POSIX 系统要求文件由服务用户所有、权限为 `600`，自动创建的目录权限为 `700`、文件权限为 `600`；Windows 使用用户目录的文件访问控制，部署时应限制到服务账号。

API 和所有 Worker 应配置同一个密钥来源。配置通过服务进程的环境变量提供，修改后重启服务；`.env` 文件不会被自动加载。配置无效、文件不存在或权限不足时操作失败，已有凭据不会被覆盖，也不会降级为明文存储。解密不会生成缺失的密钥。保留原密钥才能恢复已有凭据；直接替换密钥会使旧密文无法解密。

跨系统迁移带上数据库和对应密钥文件（或在目标环境注入同一个 `NODE_FLOW_CREDENTIAL_KEY`），将目标服务的 `NODE_FLOW_CREDENTIAL_KEY_FILE` 指向该文件，恢复权限后启动 API / Worker。凭据删除不会删除共享密钥。旧版凭据格式不再支持，需要重新录入。

## 工作流校验

`POST /api/workflows/validate` 接收完整工作流文档，返回按节点和连线组织的问题项，覆盖节点类型、端口、配置、表达式语法与结构。校验会检查表达式的基本语法，但不会静态证明运行时路径一定存在。保存和运行前都会执行权威校验，画布拖线使用同一套端口规则。
