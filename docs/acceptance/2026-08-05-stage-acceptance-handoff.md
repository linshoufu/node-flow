## 1. 验收结论

**阶段性有条件通过。**

项目已经不是只有画布和几个测试节点的 Demo。当前代码具备通用 Python 节点 SDK、节点包发现、声明式表单、动态端口、图连接校验、分支与循环、子工作流、变量和本地凭据、版本与发布、Webhook/定时触发、执行队列、取消与超时、节点级输入输出和日志等完整骨架；测试相关节点只是现有 29 个内置节点中的第一批领域节点。

当前版本适合继续作为**本地单开发者工作流工作台**迭代，也可以交给下一位 Agent 接手开发。它还不适合直接作为可暴露到公网、供普通用户使用的正式产品发布，主要原因是工作树尚未形成 Git 基线、没有认证和执行隔离、移动端仍有布局问题，部分超大模块还需要继续拆分。

## 4. 浏览器验收证据

在真实开发服务上完成以下操作：

1. 打开新建页，确认 29 个节点、通用/测试模板、画布、配置面板和运行抽屉均为中文。
2. 应用“手动处理数据”模板，确认两个节点和一条连线正确生成。
3. 点击添加“延迟”节点，并从“记录日志”的输出端口拖到“延迟”的输入端口，连线成功。
4. 运行模板，画布显示节点成功状态、执行次数和输入输出数量。
5. 打开“记录日志”的节点运行详情，确认输入、输出、事件和 `INFO` 日志可查看。
6. 把延迟设为 5 秒，运行后点击取消；取消按钮可用，最终工作流状态为“已取消”。当前 Python 节点完成后停止，符合协作式取消设计。
7. 直接打开已保存工作流 URL 并刷新，节点和连线均恢复。
8. 从模板首次自动保存后，URL 自动切换到持久工作流地址；刷新仍能恢复。
9. 在干净页面检查浏览器控制台，无应用 warning/error。

浏览器自动化的低层拖动不能稳定产生 HTML5 节点库 `dataTransfer`，因此本轮没有把“从节点库卡片拖到画布”标记为人工浏览器已验证；点击添加已验证，`FlowCanvas` 与 `NodePalette` 的组件测试覆盖拖放坐标和回退点击路径。建议下一位 Agent 再做一次真实鼠标拖放确认。

验收过程中创建的两个临时工作流已通过 API 删除，没有保留测试数据。

## 5. 本轮验收修复

### StrictMode 下工作流深链接失效

生产入口启用 React `StrictMode`。旧实现第一次挂载时开始加载 URL 中的工作流，随后 StrictMode 清理使该请求失效；第二次挂载却复用第一次的 Promise，所以即使 API 返回 200，页面仍回退到 `/workflow/new`。

修复内容：

- `useWorkflowRouteController` 在稳定挂载的微任务中发起初始路由请求。
- 第一次 StrictMode 探测挂载会在微任务执行前清理，第二次挂载只发起一次有效请求。
- 直接 URL 的 App 测试改为在 `StrictMode` 下运行。

复验结果：直接深链接、刷新恢复、模板首次自动保存后的持久 URL 均通过；相关 110 项测试和全量 932 项前端测试通过。

## 6. 未解决问题与风险

### P0：交接前必须处理的版本基线风险

当前工作区不是可恢复的交付基线：验收前统计为 66 个已修改条目、261 个未跟踪条目，共 327 个状态条目；仅已跟踪 diff 就约有 35,994 行新增和 3,109 行删除。大量核心后端、前端组件、测试和文档仍未提交。

下一位 Agent 不应执行 `git reset --hard`、`git clean` 或批量丢弃文件。第一优先级应是审查 `.tmp/`、`tmp/`、`*.orig`、报告和外包目录，把生成物加入忽略或移出交付范围，再按 SDK/后端、前端、文档拆分提交，建立一个可回退基线。

### P1：不能公网部署的安全边界

- 没有用户认证、权限和多租户隔离。
- Python 节点与主机处于同一信任边界，可执行任意本地代码，不是沙箱。
- 本地凭据库不是生产级密钥管理系统。
- 当前服务应继续只绑定 `127.0.0.1`，不要直接暴露到公网。

### P2：移动端横向溢出

在 390x844 视口中，`documentElement.scrollWidth` 为 432px；顶部 `breadcrumbs` 的“主流程”元素位于 x=371 到 x=432，造成约 42px 横向溢出。顶部工具栏虽能纵向换行，但仍需调整 breadcrumb 的换行/宽度约束，并增加 390px 浏览器或样式回归测试。

### P2：超大模块仍是维护风险

- `apps/web/src/App.tsx`：1836 行。
- `apps/api/nodeflow_api/storage.py`：1794 行。
- `apps/api/nodeflow_api/executor.py`：1524 行。
- `apps/api/nodeflow_api/main.py`：1257 行。

前端已经拆出二十余个 controller/action hook，但 App 仍承担大量装配；后端的路由、存储和执行器也应按运行、发布、节点包、凭据等领域继续拆分。拆分必须先补契约测试，避免把当前稳定行为改坏。

### P3：交互和无障碍细节

- 画布工具栏有两个按钮都使用 `aria-label="复制所选节点"`；其中一个实际是复制/克隆动作，名称应区分。
- 把一个输出端口拖到另一个输出端口时，中文提示显示“不能把节点连接到自己”，没有准确说明方向错误。
- 节点库真实鼠标拖放仍需人工复验。

### P3：文档与工程化债务

- 多份历史 plan 的 checkbox 未同步，不能据此判断实现状态；应以代码和测试为准，后续可补完成记录而不是机械勾选旧步骤。
- 仓库没有可见的 CI 配置，当前质量门槛依赖本地执行。
- pytest 有 Starlette `TestClient`/httpx 弃用警告，需要跟随依赖升级处理。
- README 的“当前不支持”只列出三项，没有完整说明执行隔离、部署和公网安全边界。

## 7. 下一位 Agent 的推荐顺序

1. **建立 Git 基线**：审查 327 个状态条目，排除生成物，按领域形成可回退提交；不要把全部变更压成一个不可审查提交。
2. **修复验收遗留 UI 问题**：移动端 breadcrumb 溢出、重复 aria 名称、错误连线提示，并做浏览器复验。
3. **继续拆 App 装配层**：优先抽离资源管理弹层和工作流问题定位编排，保持 controller 的文档作用域和迟到请求隔离规则。
4. **拆后端领域边界**：先拆 `main.py` 路由，再拆 `storage.py` 仓储；执行器只在有完整行为测试时调整。
5. **补 CI 和交付脚本**：前端测试、后端测试、生产构建、节点 doctor、diff check；随后再考虑容器化或桌面封装。
6. **决定下一产品边界**：若仍是个人本地工具，优先稳定节点开发体验；若要给别人或联网使用，认证、权限、执行隔离和密钥管理必须先于新增节点。

## 8. 接手命令

```powershell
cd D:\learn\node-flow

# 后端，端口 8150
pnpm dev:api

# 新终端：前端，端口 5273
pnpm dev:web

# 分开运行，避免组合命令超过 Agent 默认超时
pnpm --filter @node-flow/web test
pytest tests/api -q
pnpm build:web
pnpm doctor:nodes
git diff --check
```

本地数据默认位于 `D:\learn\node-flow\node-flow.sqlite3`。独立 Worker 使用 `pnpm dev:worker`，并应与 API 使用同一个 SQLite 数据库和一致的并发配置。
