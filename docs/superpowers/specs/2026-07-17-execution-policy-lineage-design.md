# 统一错误策略与运行谱系设计

**状态：** 已确认，待实施计划审阅  
**目标：** 将节点异常从各 Python 节点自行约定的行为，升级为工作流运行时统一管理的执行策略；同时为跨工作流执行建立稳定的运行谱系数据契约。

## 背景

当前 Node Flow 已经具备 Python 节点端口契约、结构化循环、运行事件、取消和节点级运行详情。异常行为仍不统一：有些节点把业务失败作为 `error` 输出返回，有些节点抛异常并终止整个运行；循环节点又拥有单独的 `continue_on_error` 配置。这样会让节点作者承担运行时策略，也使用户无法在同一个位置理解失败后的路径。

本阶段借鉴 n8n 的执行器职责划分：节点实现负责业务，执行器负责调度、重试、取消和运行数据；错误处理规则属于工作流节点配置而非节点脚本。n8n 对子工作流和错误处理也都保存可追溯的执行数据，本设计先建立相同的谱系契约，不在这一阶段引入调度器、Webhook 或跨工作流调用节点。

## 范围与非目标

本阶段完成：

- 节点级失败策略与重试配置，旧工作流保持原有的“失败即停止”语义。
- 所有节点类型的统一异常捕获、脱敏、重试事件和最终处理事件。
- 标准化错误对象，供错误端口、运行事件和节点运行详情共用。
- 运行记录上的父子谱系字段，以及前端可读取、展示和导航这些字段的通用接口。
- 配置面板、画布状态和运行详情的中文产品体验。

本阶段不完成：

- `Execute Workflow`/跨工作流调用节点、子运行创建、父子运行的实际跳转来源。
- 定时、Webhook、队列 worker、持久化等待或并行调度。
- 凭据管理、在线编辑 Python、工作流级错误处理工作流。
- 指数退避、按错误类型重试和强制终止正在运行的 Python 代码。

## 数据模型

### 节点执行策略

给 `WorkflowNode` 增加可选 `execution` 字段。省略时归一化为下列默认值，因此旧文档的运行结果不变：

```json
{
  "onError": "stop",
  "retry": {
    "maxAttempts": 1,
    "delaySeconds": 0
  }
}
```

字段定义：

- `onError`: `stop`、`continue` 或 `errorOutput`。
- `retry.maxAttempts`: `1..5`，包含首次执行；`1` 表示不重试。
- `retry.delaySeconds`: `0..60`，每次重试前固定等待秒数。

三种失败策略的精确定义：

| 策略 | 最后一次尝试失败后的行为 | 下游行为 | 整体运行 |
| --- | --- | --- | --- |
| `stop` | 记录最终失败，抛出运行错误 | 后续节点不执行 | `failed` |
| `continue` | 记录“失败已处理”，不产生端口输出 | 该节点的直接下游不激活；其他已激活分支继续 | 可 `succeeded` |
| `errorOutput` | 记录“失败已路由”，产生保留的 `error` 输出 | 仅 `error` 端口的下游被激活 | 由后续图决定 |

`errorOutput` 只能用于节点声明了名为 `error` 的输出端口、且该端口至少有一条有效连线时；保存和运行前校验都必须给出可定位的问题。这样不会出现配置为“路由错误”却静默吞掉失败的运行。

正常的业务 `error` 输出仍是节点脚本自己返回的数据，保持现有语义。只有 Python `execute()` 抛出的异常、表达式解析失败、配置实例化失败或输出校验失败才进入统一策略。

### 标准错误对象

执行器将所有可处理异常转换为 JSON 安全的 `NodeExecutionError`：

```json
{
  "message": "请求超时",
  "type": "TimeoutError",
  "attempt": 2,
  "nodeId": "request_1",
  "scope": ["foreach_1", "iteration:3"],
  "timestamp": "2026-07-17T00:00:00+00:00"
}
```

运行事件中的错误对象和错误端口中的值使用相同字段。仅事件可附带经现有 `_redact()` 处理后的 `traceback` 与节点日志；错误端口不包含堆栈，避免把实现细节送到下游业务数据。

取消和工作流超时不受节点 `execution` 策略影响：它们始终终止运行。重试等待期间也检查协作式取消。

### 运行谱系

`RunRecord` 和 `runs` 表增加以下可空字段：

- `parent_run_id`: 创建该运行的父运行 ID。
- `parent_node_id`: 父运行中发起该运行的节点 ID。

两者必须同时为空或同时有值。当前人工运行始终为空；本阶段不制造子运行。`Storage.create_run()` 和 API 响应接受可选父级数据，以便下一阶段的跨工作流节点无需破坏数据库、API 或前端类型。

运行详情模型提供 `parentRunId`、`parentNodeId`，并预留 `childRunIds`（当前为空）。前端在这些字段存在时显示“父运行”入口；入口通过既有运行加载能力打开目标运行。没有谱系时不展示占位控件。

## 后端架构

### 纯策略模块

新增 `execution_policy.py`，只定义并校验：

- `NodeExecutionPolicy`、`RetryPolicy` 和默认值。
- 规范化旧节点的策略。
- `errorOutput` 端口前置条件。
- `NodeExecutionError` 的安全序列化。

该模块不访问 SQLite、不执行节点，方便独立 pytest 覆盖边界值与兼容性。

### 执行器边界

`WorkflowExecutor._execute_node()` 重构为两个层次：

1. `_run_node_attempt()` 执行一次节点、收集日志、解析表达式并校验输出；它要么返回声明输出，要么抛出原始异常。
2. `_execute_node_with_policy()` 读取归一化策略，发出事件，执行最多 `maxAttempts` 次，并将最终异常转换为停止、空输出继续或 `error` 输出。

所有现有特殊节点（条件、变量、转换、循环、测试汇总）都通过同一策略封装，不再各自重复 `node_failed` 事件。`ForEach` 的 `continue_on_error` 保留为循环体迭代级语义，优先于“某个迭代体失败后是否继续下一项”；其中节点本身的策略仍决定该迭代内某个节点如何结束。

事件顺序固定：

1. `node_started`，包含 `attempt`。
2. 中间失败：`node_retry_scheduled`，包含 `error`、`attempt`、`next_attempt`、`delay_ms`。
3. 最终成功：`node_succeeded`，包含 `attempt`、输出、日志、总耗时。
4. 最终停止失败：`node_failed`，包含 `error`、日志、总耗时和 `handled: false`。
5. 最终被策略处理：`node_failed` 后紧跟 `node_error_handled`，后者包含 `mode`、错误数据与可选 `outputs`；前者仍保留真实失败诊断。

这样任何运行详情都能同时展示“该节点失败过”和“工作流如何继续”，不把已处理异常伪装成成功。

### 验证与持久化

- `schemas.py` 承载 Pydantic 文档模型和 API JSON 别名。
- `validation.py` 调用策略校验；问题路径为 `nodes.<id>.execution...`，嵌套子流程沿用既有路径规则。
- `storage.py` 以增量迁移向既有 SQLite `runs` 表添加谱系列；查询、创建与反序列化完全保留字段。
- API 创建运行仍使用空谱系，历史运行接口直接返回字段。

## 前端体验

### 节点配置

配置面板增加“失败处理”折叠分区：

- 选择组：`失败即停止`、`失败后继续`、`走错误端口`。
- 数字步进控件：`最多尝试次数` 与 `重试间隔（秒）`。
- 选中“走错误端口”但节点无 `error` 输出时，控件禁用并显示中文原因。
- 仅当用户调整过策略时才在工作流 JSON 写入 `execution`，使旧文档保持最小差异。

画布节点仅在非默认策略时显示紧凑的策略徽标；不泄露内部字段名。保存前和运行前问题中心会定位到该节点与对应配置字段。

### 运行观察

运行状态模型新增 `handled` 节点状态，中文标签为“失败已处理”。它使用明显但非终止性的橙色样式；整体运行成功时，用户仍可看出曾有失败。

节点运行详情：

- 在执行批次卡中显示“第 N 次尝试”。
- 事件时间线显示“等待重试”和“失败已处理”。
- 错误端口数据作为普通输出数据可展开查看。
- 搜索把尝试次数、策略和错误对象纳入索引。

运行抽屉的详情区域在存在父运行时展示“返回父运行”按钮。由于本阶段还不创建子运行，该入口以契约和组件测试保证可用，不在普通手工运行中出现。

## 测试策略

后端 pytest：

- 旧工作流策略缺省为 `stop`/一次尝试。
- 异常节点在 `stop`、`continue`、`errorOutput` 下的事件、下游执行和最终运行状态。
- `errorOutput` 缺端口或缺连线时的可定位保存前与运行前校验。
- 成功重试、耗尽重试、重试等待期间取消，以及取消/超时不被策略吞掉。
- 循环体中的节点策略与 `continue_on_error` 组合。
- 谱系列对新旧 SQLite 数据库的迁移、存取与 API 序列化。

前端 Vitest：

- 工作流归一化与策略配置写入。
- 配置面板的中文选项、禁用条件和最小 JSON 变更。
- 事件到 `handled` 状态的归纳、重试次数和中文显示。
- 运行详情对重试/已处理错误/父运行入口的展示与导航回调。

全量验证：`pytest tests/api -q`、`pnpm --filter @node-flow/web test`、`pnpm build:web`，以及浏览器中分别验证停止、继续、错误端口和重试成功四条路径。

## 交付边界

完成本阶段后，Python 节点作者只需要声明端口并抛出业务异常；工作流作者可以在编辑器中决定失败策略并在运行详情看到每次尝试。`parentRunId`/`parentNodeId` 已经成为稳定持久化契约，下一阶段可在不迁移历史数据的前提下实现真实的“执行子工作流”节点。
